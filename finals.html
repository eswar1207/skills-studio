1. Consistency models

Linearizability is the strongest common model: every operation appears to take effect at one instant between its start and its end, so a read always sees the latest completed write. Eventual consistency only promises that replicas converge if updates stop; reads in the meantime can be stale.

CAP: during a network partition, a system has to choose between staying consistent (refusing some requests) and staying available (answering with possibly stale data).

Q1. A read returns a value older than a write that already finished. Which model allows this?Eventual consistency allows it. Linearizability does not.
Q2. What does CAP force you to choose, and when?Consistency or availability, and only while a network partition is happening.

2. Replication and quorums

With N replicas, a write waits for W acknowledgements and a read asks R replicas. If R + W > N, every read set overlaps every write set, so a read reaches at least one replica with the latest write. Asynchronous replication is faster but can lose writes the leader acknowledged and had not yet copied when it failed.

Q3. N = 5, W = 3. What is the smallest R that guarantees overlap?R = 3, because 3 + 3 = 6 > 5.
Q4. Why can asynchronous replication lose an acknowledged write?The leader replies before copying the write; if it fails before a follower receives it, the new leader never had it.

3. Consensus

Raft elects one leader per term. Followers that hear no heartbeat start an election after a randomized timeout, which makes split votes rare. A log entry is committed once the leader has replicated it on a majority. Two-phase commit (prepare, then commit) is not consensus: if the coordinator fails after everyone votes yes, participants block. Split brain, two leaders at once, is prevented by majority quorums and fencing tokens.

Q5. When is a Raft log entry committed?When the leader has stored it on a majority of servers.
Q6. Why does two-phase commit block?Participants that voted yes cannot commit or abort on their own; they wait for the coordinator.
Q7. What problem do randomized election timeouts solve?Many followers starting elections at once and splitting the vote.

4. Time and ordering

Lamport clocks give an order consistent with causality: if A happened before B, A's timestamp is smaller. They cannot tell whether two events were concurrent. Vector clocks can. Idempotent operations make retries safe, and consistent hashing moves only about 1/N of keys when a node joins or leaves.

Q8. Two events have Lamport timestamps 4 and 7. Did the first cause the second?Not necessarily. A smaller Lamport timestamp doesn't prove causality; you need vector clocks to tell.
Q9. Why should a payment API be idempotent?A client that times out will retry. Idempotency (for example, an idempotency key) makes the retry charge only once.
